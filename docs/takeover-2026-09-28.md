## 1. 项目是做什么的

CTFScanner：面向 **CTF / 授权渗透测试** 的资产测绘与漏洞初筛框架。把手工渗透的前半段产品化：

```
subdomain → takeover → portscan → probe → cert → screenshot → osint → jsmine
→ dirscan → vulnscan → intel → heuristic → github     （13 个阶段，runner.STAGE_ORDER 是唯一真相）
```

两种入口：CLI（`cli/client.py`）与 Flask Web 控制台（`run_gui.py`，仿 ARL）。
数据落 SQLite（`data/scanner.db`），产物落 `logs/task_<id>_<ts>/`。

**不可越过的红线**：仅用于自有或书面授权目标；检测一律非破坏性（只探测，无爆破 / 无写操作 / 无 DoS 延时）。

### 6.1 `screenshot` 对**自签证书的 HTTPS 站点必然失败**，而且被误标成"环境问题"（P0 功能缺陷）

**现象**：`run_devflow.py` 的截图阶段每次都失败。`CHANGELOG_AI.md` 续62 条目把它写成
「本机无头浏览器截图失败，`screenshot/shot` 记为 N-A（**环境问题**，非覆盖缺口）」，
`scanner/devflow.py` 的向量里也写着 `na_log=("截图失败", "…（环境问题，见阶段日志）")`。

**归因是错的**。我用**生产函数** `screenshot.capture()` 做了对照实验（本机夹具 `devfixture` 的
自签 HTTPS 口 vs HTTP 口，浏览器 = Edge）：

| 组 | 目标 | 参数 | 结果 |
|---|---|---|---|
| 1 | `https://…`（自签） | **现状参数** | **失败**，浏览器报 `net::ERR_CERT_AUTHORITY_INVALID`，png **0 字节** |
| 2 | `http://…` | 现状参数 | 成功（13512 字节） |
| 3 | `https://…`（自签） | 现状 + **`--ignore-certificate-errors`** | **成功**（13512 字节） |
| 4 | `https://…`（自签） | `--headless=old` + 该参数 | 成功 |
| 5 | `https://…`（自签） | `--headless=old` 无该参数 | 失败 |

**根因**：`scanner/screenshot.py::capture()` 的 argv 里**没有** `--ignore-certificate-errors`
（全仓 grep：该参数**从未出现过**）。浏览器遇到不可信证书直接拒绝加载，`--screenshot` 一个字节都不产出。
第 3 组证明"只加这一个开关就从失败变成功"，第 4/5 组证明**与 `--headless=new` 无关**
（那是 `browser_e2e.py` 里另一回事：`--headless=new` 在 Windows 上拿不到 stdout）。

**影响**：**任何自签 / 过期 / 私有 CA 的 HTTPS 站点永远截不到图** —— 而这恰恰是 CTF 与内网授权目标的
常态（本项目 `certs.py` 取证就是刻意 `CERT_NONE`，`README` 也写着"CTF 目标多为自签/过期"）。
更糟的是它**被记成"环境问题"**，于是续62 那句"0 覆盖缺口"是**把真缺陷解释掉了**才得到的
—— 这正是 `AGENTS.md §6.1` 反复警告的「观测到异常 ≠ 归因正确」。

**已修**（续64）：`scanner/screenshot.py` 补 `--ignore-certificate-errors`（抽成模块级 `_FLAGS`）；
端到端覆盖在 `tests/smoke.py [7z]`（对 `127.0.0.1` 形态的自签夹具 URL 调**生产函数** `capture()`）。
修复后实测：自签 HTTPS **13512 字节**（与 HTTP 组完全一致），把开关去掉即回 0 字节。

**顺带澄清一处**：修好后 `run_devflow.py` 的 `screenshot/shot` 向量**仍是 N-A**（汇总仍是
**18 OK / 0 MISS / 17 N-A**，不是我先预期的 19/16）—— 但原因**换了**：自检的截图目标是夹具
**主机名**，而自检的 DNS 覆盖是**本进程**的 `socket.getaddrinfo` 打桩、**浏览器子进程看不见**，
浏览器自己解析得 NXDOMAIN。实测同一夹具：`https://127.0.0.1:<port>/` 能截、`https://www.devfixture.test:<port>/`
不能。这是**自检环境的限制**（与已登记的"subfinder/httpx/nmap 不认 DNS 覆盖"同类），
**不是截图功能的问题** —— 已在 `AGENTS.md §7` / `docs/roadmap.md` 如实登记，并把 N-A 的理由
改成这条真实原因（原来写的「本机无头浏览器截图失败」会让人以为功能坏了）。

### 6.5 `AGENTS.md §9` 的换行符规矩**与仓库事实不符**（463 个文本文件里 69 个含 LF-only）

§9 原文：「**换行符：仓库内文本文件以 CRLF 存储**（仓库级 `core.autocrlf=false`），
**禁止提交 LF-only 的文件**。」—— **这句不成立**。我扫了全部 463 个被跟踪的文本文件
（**已提交状态**，`git show HEAD:<file>` 取字节，不是工作区脏）：

| 形态 | 例子 |
|---|---|
| **整体就是 LF** | `scanner/extdom.py`(318 行)、`scanner/intel.py`(282)、`scanner/iprecon.py`(278)、`scanner/stages/subdomain.py`(266)、`scanner/fofa.py`(261)、`config/dicts/cdn_cname.txt`(291) |
| **混合** | `tests/smoke.py`（8653 CRLF + **1494 LF**）、`cli/client.py`(279+108)、`gui/app.py`(2948+52)、`docs/usage.md`(507+1)、`docs/pipeline.md`(528+1) |
| **整体 CRLF** | `scanner/db.py`、`scanner/utils.py`、`scanner/screenshot.py` |

**为什么这不是吹毛求疵**：
1. 下一个接手者若信这条规矩，会去"修"那 69 个文件 → **海量 EOL 假变更**，而 §9 自己正是在警告
   这种后果（"2811 行纯 EOL 假变更、review 完全失效"）；
2. 本轮就付了学费：工程师因为"应当 CRLF"的假设，Edit 工具把 `tests/smoke.py`、`docs/pipeline.md`
   这类**混合 EOL** 文件整体归一成 LF，只好用 `git show HEAD:` 取原始字节逐行重建才通过自查。

真正成立、且所有人一直在用的判据是另一个：**"不要改变文件原有的 EOL 形态"** ——
`git diff --numstat` 与 `git diff --ignore-cr-at-eol --numstat` **逐文件一致**（对全 LF 文件同样成立）。
**已按事实改写 §9**（续64）。

### 6.6 IDN 的缺口比文档记录的更大：**连 punycode 形态都不被支持**（续65 已修）

`AGENTS.md §7` 原来只登记「IDN / 中文域名整体不被识别」，听起来像"只不支持中文"。
实际实测：**`is_domain('xn--fsqu00a.xn--fiqs8s')` 也是 False** —— 因为 TLD 正则要求 `^[a-z]{2,24}$`，
而 punycode 的 `xn--fiqs8s` 含数字与连字符。**punycode 域名（ASCII）同样被丢**，只是没人注意到。

而"域名形态"这个口径在仓库里被**复制成了四份**（这就是缺口能长期藏住的原因）：
`utils._DOMAIN_RE`、`targets.py` 自己的 `DOMAIN_RE`（带 `re.I`、`{2,}`，**已与前者不一致**）、
`iprecon._DOMAIN_OK` + `normalize_domain` 的 `.isalpha()`、`jsmine` 的 host 判定。
第五处是数据：`config/dicts/tlds.txt` 的 **`xn--` 条目为 0** —— `tools/import_tlds.py` 按
"IDN 后缀永远不会命中"的**错误推理**把 447 条非 ASCII 后缀整批滤掉（那个 ASCII 正则其实**能**匹配
punycode 形态；tldextract 只是把 IDN 后缀存成了 Unicode）。

**续65 的收口思路**：归一化**只留一个入口** `utils.to_ascii()`，并把"库里只可能有 punycode"
做成 `db.insert_subdomains()` 的**结构性保证**（咽喉点），而不是靠"N 个调用点都记得归一"。
QA 独立复核又挖出**两条本轮原先没做到的路径**：`osint._domain_of` 会把外部情报返回的 Unicode
域名**直接落库**（破坏本轮自己的不变量、会造成同域两形态重复行）；URL 形态目标
（`https://例子.中国/x`）未归一。两条已一并收口。

### 7.3 一条可复用的踩坑（留给下一个接手者）

修 §6.1 时我给的方案是 `Path(p).resolve()` 做绝对化 —— **工程师反对并实测证明它对**：
本机 **Python 3.9.0** 上 `Path('rel-shot.png').resolve()` 返回 `rel-shot.png`（**仍是相对**），
等于"看着修了其实没修"。触发条件很窄：**只有"裸文件名、不带目录成分"**才这样
（`logs/task_1/x.log` 就正常绝对化）—— 因为 CPython 3.9 的 Windows 分支向上回退到空串时
直接返回原路径，而 `os.path.split('rel-shot.png')` 立刻就是 `('', 'rel-shot.png')`。
改用 `Path(p).absolute()` 才是对的。**我扩查了全仓另外 19 处 `.resolve()`**（`__file__` 派生 9 处、
`gui/app.py` 的 `log_file` 派生、`toolmgr.py` 的配置值，后者 `except ValueError` 有兜底）
—— **没有第二处可达的同类缺陷**。教训：**给下属的"修法"也要经得起实测**，别只给结论。

`docs/roadmap.md` 写「分布式节点认领需要先替换 SQLite」—— 但有一个**轻得多的方案**可以绕开数据库替换：

**Phase 1（拉取模式，零 schema 变更）**

- 节点跑 `cli/client.py --node <控制台URL>`：轮询控制台的 `/api/node/claim`（HTTPS + 现有
  `gui.token`/账号认证）认领排队任务 → 在**节点本地**用自己的 SQLite 跑完整流水线 →
  结果以 **JSONL 导出**后 POST 回 `/api/node/results` → 控制台按 `(target, source)` 去重导入。
- 节点无状态、不需要共享数据库、复用现有 HTTPS 认证与限速。

**Phase 2**：把队列的认领/确认抽成 `queue/backend.py` 接口（`sqlite` / `http` 两个实现）。
