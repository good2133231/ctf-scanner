## 1. 项目是做什么的

CTFScanner：面向 **CTF / 授权渗透测试**的资产测绘与漏洞初筛框架。把手工渗透的前半段流水线产品化：

```
subdomain → takeover → portscan → probe → cert → screenshot → osint → jsmine
→ dirscan → vulnscan → intel → heuristic → github      （13 个阶段，runner.STAGE_ORDER 是唯一真相）
```

两种入口：CLI（`cli/client.py`）与 Flask Web 控制台（`run_gui.py`，仿 ARL，9 栏侧边栏 + 任务详情 10 页签）。
数据落 SQLite（`data/scanner.db`），产物落 `logs/task_<id>_<ts>/`。

**不可越过的红线**：仅用于自有或书面授权目标；检测一律非破坏性（只探测，无爆破 / 无写操作 / 无 DoS 延时）。

## 2. 当前架构

```
入口层   cli/client.py · gui/app.py（1607 行）+ 17 个模板 + 原生 JS/CSS
编排层   scanner/runner.py（StageContext / PipelineRunner / 协作式取消 / 断点续扫 / 追加执行）
阶段层   scanner/stages/*（13 个）
检测层   pocs/engine.py（nuclei 兼容子集）· owasp/checks.py（14 项）· fingerprint.py · evasion.py
基础层   utils.py（HTTP 唯一出口）· config.py · throttle.py（F2 统一并发/限速/预算）· log.py
存储层   scanner/db.py（SQLite，1089 行，每次调用独立连接 + _WRITE_LOCK）
```

规模：Python 约 14.5k 行（其中 `tests/smoke.py` 约 4.7k 行是唯一回归门禁）；配置 165 个叶子键
（DEFAULTS ↔ `config/settings.yaml` ↔ GUI 策略页 POST 三方一致，我已逐键核对，见 §6.1）。

三条贯穿性设计（改代码时必须保住）：外部工具优先 + 内置兜底；所有 HTTP 走 `utils.http_request`；
**漏洞 ≠ 线索**（`intel` / `heuristic` / `github` 只写 `leads`，不写 `vulns`、不计入漏洞数）。

## 6. 我发现、但此前文档没有记录的问题

按严重度排序。

### 6.1 「全 13 阶段能不能串起来跑完」从来没有回归门禁

现有 smoke 里：`[3]` 只跑 `probe + vulnscan` 两个桩阶段，`[5p] 3c` 只真跑 `dirscan`，
`[6q]`/`[6r]`/`[6s]` 全是桩掉 `run_task`。**没有任何一条用例真跑完整条 13 阶段流水线。**
续10（2026-09-23）手工跑过一次，但那**时**只有 11 阶段 —— `cert`、`github`、目录递归、
追加执行、断点续扫、F2 门控都是后来加的，之后再没整条跑过。

本项目自己的教训反复写着"只有真跑才暴露得出来"（`AGENTS.md §6.1` 举了两次假测试），
而这条最大的集成面恰恰是最没覆盖的。**本次已实跑一次**（见 §7），并已固化为 smoke `[6u]`。

### 6.2 `config/settings.yaml` 里 `fofa.enabled: true`，与 DEFAULTS 和全部文档口径冲突，且会真花配额

- `scanner/config.py` 的 `DEFAULTS["fofa"]["enabled"] = False`，`README` / `roadmap` / `AGENTS`
  三处都写「osint **默认全关**」；但被 git 跟踪的 `config/settings.yaml` 里这一项是 **`true`**。
  （我逐键比对了全部 165 个叶子键：**只有这一项**与 DEFAULTS 不同。）
- 默认阶段集是**全 13 阶段**（CLI `-p` 缺省、`gui/app.py` 的 `stages = [...] or list(STAGE_ORDER)`），
  `osint` 在其中；而 `config/keys.yaml` 里填着**真实的 FOFA 凭据**（email 22 字符 / key 32 字符）
  与 **GitHub token**（93 字符）。
- 后果：**每一次默认任务都会真的去查 FOFA 并消耗配额**，而文档告诉使用者"默认关"。
- 我没有擅自关它 —— 很可能是用户为校准阈值主动开的（`AGENTS.md §7` 有"FOFA 三种反查已真实跑过，
  key 已配"的记录）。**已在 `AGENTS.md §7` 登记，等用户确认。**

### 6.3 `docs/roadmap.md`（自许为"什么已落地"的权威清单）漏了 5 轮

## 8. 下一步建议（按价值排序）

1. **给「全阶段端到端」补回归门禁**（本次已做，`[6u]`）——理由见 §6.1。
2. **请用户确认 §6.2 的 `fofa.enabled`**：要么把它改回 false 与文档对齐，要么把文档口径改成
   "默认开、会花配额"。**这是当前唯一会让工具在用户不知情时产生外部开销/外发请求的地方。**
3. **真实授权目标上跑一遍全 13 阶段** —— 至今只有本机靶场与回环样本。这是"POC 置信度实测校准"
   与"osint 阈值二次校准"共同的前置条件，**必须用户先指定并授权目标**。
4. **IDN / 中文域名支持**（`utils.is_domain` 的 TLD 要求纯 ASCII，实测 `例子.中国` → False、
   目标解析直接判 `unknown` 被丢弃）。对中文使用者是真实缺口，`AGENTS.md §7` 已登记为"需另开一轮"。
5. 之后才轮到 `docs/roadmap.md` 里的长期项（任务队列 / 多用户与审计 / HTTPS 指引 / 分布式节点 /
   工具版本管理）—— 当前瓶颈不是"功能不够"，而是"新落地的默认行为缺少真实数据校准" +
   "最大的集成面没有回归门禁"。
